# 뚝딱 프로젝트 개발 컨벤션

> 이전 LMS 프로젝트(`ohgiraffer_fe`) 컨벤션을 검토해 뚝딱 프로젝트에 맞게 조정했다.

---

## 1. 에러 메시지 처리 원칙

화면에 노출하는 에러 메시지는 백엔드가 내려주는 에러코드 + 메시지를 그대로 사용한다. 프론트에서 임의로 재해석/하드코딩하지 않는다. 단, 다음은 예외로 프론트가 자체 메시지를 구성한다:
- 네트워크 자체 실패(백엔드 응답을 아예 못 받은 경우)
- 입력값 검증 실패 등 프론트 단계에서 먼저 걸러지는 경우

에러코드별 분기가 필요하면 하드코딩해서 흩어놓지 말고 한곳에 상수/매핑으로 관리한다.

## 2. 컴포넌트 분리 원칙

모든 페이지/기능 작업은 컴포넌트 분리를 기본 전제로 진행한다. 하나의 큰 컴포넌트에 로직과 마크업을 몰아넣지 않는다.

**(AI 어시스턴트 작업 시 필수 절차)** 컴포넌트 분리를 실제로 진행하기 전에, 예상되는 파일 구조도(어떤 파일이 새로 생기고 무엇을 담을지)를 먼저 제시하고 사용자 확인을 받은 뒤 진행한다. 확인 없이 임의로 파일을 나누지 않는다. (`folder-structure-guide.md`의 "애매하면 먼저 확인받기" 원칙과 같은 맥락 — 컴포넌트 분리 시에도 동일하게 적용)

## 3. 폴더 구조 — FSD 기준

이 프로젝트는 `folder-structure-guide.md`에서 정한 FSD 기반 구조(`app/widgets/features/entities/shared`)를 따른다. 이전 프로젝트의 `components/features/lib/services` 구조는 쓰지 않는다.

- `app/`은 라우팅 파일(`page.tsx`, `layout.tsx`, `loading.tsx`)만 갖는다. `page.tsx`는 `widgets/`, `features/`를 불러와 조립만 하고 로직을 직접 작성하지 않는다.
- 클라이언트 상태·상호작용 때문에 여러 컴포넌트를 미리 조합해야 하는 경우, 그 조합 컴포넌트를 `~~~Client.tsx`로 이름 붙인다. 위치는 조합 범위에 따라 다르다:
  - 한 feature 안에서만 조합되면 → `features/{feature}/ui/~~~Client.tsx`
  - 여러 feature/entity를 넘나들며 조합되면 → `widgets/{widget}/ui/~~~Client.tsx`
- `entities/{entity}/`, `features/{feature}/` 슬라이스 내부는 아래 구성을 기본으로 한다:
  - `ui/` — 컴포넌트
  - `model/` — 이 슬라이스 전용 상태/훅
  - `api/` — 이 슬라이스의 API 호출 함수 (4번 참고)
  - `types.ts` — 이 슬라이스의 타입 정의
- `shared/ui/shadcn/`: `npx shadcn add`(또는 CLI)로 생성된 컴포넌트 파일은 여기에 모아둔다. 직접 작성한 커스텀 컴포넌트와 CLI 자동생성 파일을 구분해서, 어떤 파일이 CLI로 재생성·업데이트될 수 있는지 한눈에 알아보기 위함이다. `shared/ui/` 바로 아래에는 직접 작성한 컴포넌트만 둔다.

## 4. API 호출 계층 — `api/` 세그먼트 (services 방식)

백엔드가 별도 팀(2명)이 운영하는 독립 API 서버이므로, Next.js Server Actions(`actions.ts`)가 아니라 **전담 API 호출 계층**을 쓴다.
- `shared/lib/apiClient` — 공통 fetch 클라이언트(헤더/에러 처리/재시도 등 공통 로직) — `folder-structure-guide.md`의 shared 레이어 예시와 동일한 위치
- `entities/{entity}/api/`, `features/{feature}/api/` — 각 도메인의 실제 API 호출 함수

UI 로직과 API 호출 로직을 분리해서, 컴포넌트에서 fetch를 직접 호출하지 않는다. 구체적인 폴더 구조/코드 예시는 `api-layer-guide.md` 참고.

## 5. 중복 요청 방지 원칙

결제/삭제 등 부작용이 있는 액션은 버튼 `disabled` 상태만으로 막지 말고, `useRef` 기반의 동기 가드(예: `isSubmittingRef`)를 함께 둔다. React state 업데이트는 비동기라 `disabled` 하나만으로는 빠른 연타(더블클릭)를 완전히 막지 못한다.

**AI 생성 요청에도 동일하게 적용한다.** AI 초안 생성은 토큰 비용이 직접 드는 액션이므로, 연속 클릭으로 인한 중복 생성 요청을 막는 게 특히 중요하다.

## 6. 세션 만료 공통 처리

인증이 필요한 서버 컴포넌트는 API 호출을 반드시 try/catch로 감싸고, 인증 세션 오류는 전용 리다이렉트 컴포넌트로 처리한다. 그냥 두면 예외가 그대로 전파되어 Next.js 기본 에러 화면으로 전체 페이지가 깨진다.

## 7. Fail-safe 기본값 원칙

보안/가용성에 관련된 조회가 실패했을 때, "문제없음"으로 기본 처리하지 않고 안전한 쪽으로 기본값을 둔다.

**`entities/plan`의 `PlanPolicyGuard`에 적용**: 구독 플랜 조회가 실패하면 그 사용자의 실제 플랜을 모르는 상태가 된다. 이때 "모르니 일단 허용(상위 플랜 취급)"으로 두면 결제 안 한 기능/쿼터가 새어나갈 수 있으므로, **가장 제한적인 플랜(FREE) 기준으로 간주**한다.

이건 "사용자 편의를 위해서"가 아니라 **"확인하지 못한 걸 사용자에게 유리하게 잘못 추정하지 않기 위한 안전장치"**라는 점이 중요하다. 결과적으로 서비스를 완전히 못 쓰게 막지는 않지만(그래서 편의처럼 보이지만), 목적은 유료 기능/쿼터가 새는 걸 막는 것이다. 단, 조용히 막기만 하면 유료 사용자가 혼란스러울 수 있으니 "플랜 정보를 불러오지 못해 일시적으로 기본 플랜 제한이 적용됩니다" 같은 안내를 함께 보여준다. 이 패턴을 실제 `api/` 계층 코드 수준으로 구현한 예시는 `api-layer-guide.md` 4번 항목 참고.

## 8. 무거운 라이브러리 도입 전 검토

차트·애니메이션 등 특정 UI 하나를 위해 큰 라이브러리를 새로 추가하기 전에, 순수 CSS/SVG로 충분히 구현 가능한지 먼저 검토한다.

**에디터 관련 라이브러리는 특히 더 엄격하게 검토한다.** 리치텍스트/DnD/컬러피커 등 에디터 툴바 라이브러리를 새로 도입할 때는 반드시 번들 사이즈를 확인하고 팀에 공유한 뒤 결정한다.

## 9. 중복 구현 전 공용 컴포넌트 확인

검색창, 페이지네이션, 모달처럼 여러 화면에서 비슷하게 필요한 UI는 새로 만들기 전에 `shared/ui/`에 이미 있는지 먼저 확인한다.

## 10. 타입/에러 구분

API 응답 처리 시 "서버 오류"와 "입력값 검증 오류"를 구분해서 사용자에게 다른 안내를 준다.

## 11. 네이밍 컨벤션

컴포넌트는 PascalCase, 훅은 `use` 접두사 + camelCase로 통일한다.

## 12. 주석 규칙

주석은 한국어로, 코드가 이미 보여주는 "무엇을"이 아니라 "왜 이렇게 했는지"만 남긴다.

## 13. PR 전 체크리스트

`tsc --noEmit`, `eslint` 통과를 확인한 후 PR을 생성한다. 기존에 있던 lint 경고와 이번 변경으로 새로 생긴 경고를 구분해서 확인한다.

## 14. 아이콘 사용 규칙

아이콘은 기본적으로 `lucide-react`에서 가져와 사용한다. `lucide-react`에 없는 아이콘만 예외적으로 `<path>` 기반 SVG로 직접 만들어 `public/icons/`에 추가한다.

## 15. 클릭 커서 처리

클릭 이벤트가 있는 요소는 예외 상황이 아니면 무조건 `cursor-pointer`를 명시한다.

## 16. 표(table) 인덱스 열 필수

페이지에 표가 포함되는 모든 경우, 첫 번째 열에 행 번호(인덱스)를 필수로 추가한다(`#`). 페이지네이션이 있어도 전체 데이터 기준으로 번호가 이어진다. **관리자 페이지(사업자 인증 검토 목록, 결제 기록, 배포 사이트 관리, 오류 조회 등)에 그대로 적용한다.**

## 17. 모달 컴포넌트 사용 규칙

모달을 새로 만들기 전에 공용 Modal/ConfirmModal 컴포넌트 중 목적에 맞는 걸 먼저 확인한다. 임시저장 기능이 없는 등록/작성 폼을 담을 때는 배경 클릭으로 닫히지 않게 한다(입력값 유실 방지). Escape 키와 폼 안의 "취소" 버튼은 항상 닫히도록 둔다.
